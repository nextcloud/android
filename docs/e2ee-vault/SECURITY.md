# E2EE vault security model

This document describes the security behavior of the Android E2EE vault media changes.

The vault improves local protection after the user has configured server-side Nextcloud E2EE. It does not
change the Nextcloud E2EE protocol and it does not give the server access to decrypted media or decryption keys.

## Goals

- Require biometric authentication before entering an E2EE folder.
- Keep an unlocked vault available only for a short local session.
- Lock all vault sessions after enough background time or immediately when the device is no longer interactive.
- Protect locally stored E2EE private key and mnemonic material with Android Keystore-backed encryption.
- Never request server-generated previews for E2EE media.
- Generate E2EE thumbnails only on the Android client after the vault is unlocked.
- Avoid persistent plaintext media files for E2EE image and video preview.
- Clear plaintext thumbnails, image bitmaps and video buffers when the vault locks or the viewer closes.
- Enable `FLAG_SECURE` while vault folder or vault media content is visible.

## Threats Covered

### Accidental access on an unlocked phone

Opening an E2EE folder now goes through `VaultBiometricManager`, which wraps AndroidX `BiometricPrompt` with
`BIOMETRIC_STRONG`. A cancelled or failed prompt does not browse into the folder.

The unlocked state is tracked by `E2eeVaultSession` per account and encrypted folder. The default session length
is centralized in `E2eeVaultSessionConfig`.

### App background and device lock

`E2eeVaultLifecycleManager` observes app activity lifecycle events. Vault sessions are locked when the app has
been in the background longer than the configured session duration. If Android reports that the device is no
longer interactive, all vault sessions are locked immediately.

### Plaintext thumbnails in shared or persistent storage

E2EE thumbnails are generated by `E2eeThumbnailProvider` from locally decrypted plaintext after successful vault
unlock. `E2eePreviewPolicy` blocks server preview use for encrypted files.

The first implementation uses `E2eeThumbnailMemoryCache`, an in-memory cache only. It is cleared on vault lock
and does not write plaintext thumbnails to the normal disk thumbnail cache.

### Plaintext image files left after preview

E2EE image preview uses `E2eeImagePreviewProvider` and `E2eeMediaFileLoader` to download ciphertext to private app
temporary storage, decrypt locally, decode a sampled bitmap, and then clear the plaintext byte array. The image
viewer displays the decoded bitmap in-process instead of writing a decrypted JPEG or PNG to the normal local file
path for preview.

`PreviewImageFragment` clears the bitmap and unregisters vault lock listeners when the viewer stops or the vault
locks.

### Plaintext video files left after preview

E2EE video preview downloads the complete ciphertext to private app temporary storage, authenticates and decrypts
it locally, then provides plaintext to ExoPlayer through `E2eeVideoMediaSourceHandle`.

The current implementation stores the decrypted video bytes in process memory for the lifetime of the media
source handle. It does not create a persistent plaintext video file. Closing the handle fills the plaintext byte
array with zeros.

### Recent-app and screenshot leakage

`E2eeVaultSecureWindowManager` applies `WindowManager.LayoutParams.FLAG_SECURE` while encrypted folder content or
encrypted preview content is visible. The manager is reference-counted per Activity so overlapping vault screens
do not disable the flag too early.

This prevents normal screenshots and reduces leakage through the Android recent-app snapshot for supported
platform behavior.

### Plaintext E2EE secrets in the arbitrary data table

`E2eeVaultSecretStore` stores private key and mnemonic data as an encrypted payload under
`E2EE_VAULT_SECRETS_V1`. The encryption key is generated by `AndroidKeystoreE2eeVaultSecretCipher` in
`AndroidKeyStore` with user authentication required.

Legacy plaintext `PRIVATE_KEY` and `MNEMONIC` values are migrated on first access. Migration verifies that the
encrypted payload decrypts back to the same values before deleting legacy entries.

## Threats Not Covered

### Compromised device or OS

The vault does not protect against a rooted device, a compromised Android OS, kernel-level access, malicious
instrumentation of the app process, or malware with elevated privileges.

### User already authenticated inside the vault

After successful biometric authentication, the user can view the vault during the active session. A user who can
view media can still intentionally export, photograph, record or otherwise disclose the content.

### Memory forensics of the app process

Image bitmaps and video plaintext buffers exist in process memory while content is being displayed. The code
clears byte arrays and releases bitmaps when practical, but Android and library internals can keep copies outside
direct application control.

### Server-side E2EE protocol limitations

The current file encryption format uses AES-GCM with one file key, one nonce and one authentication tag per file.
It is not chunked and does not provide authenticated random access to independent byte ranges.

For videos, this means true progressive E2EE streaming with HTTP Range semantics is not implemented. The safe
client behavior is to download the full ciphertext, authenticate and decrypt it locally, then pass plaintext only
to the in-app player.

### Keystore implementation limits

Android Keystore security depends on the device implementation, OS version, enrolled biometric strength and lock
screen configuration. The current key uses `BIOMETRIC_STRONG` authentication parameters on Android 11 and newer,
and the older validity-duration API on older supported versions.

### Existing plaintext files from older app behavior

This vault path prevents new preview flows from writing plaintext media files. It does not automatically find and
delete every plaintext E2EE media file that may have been produced by older app versions or by explicit offline
download behavior outside this vault preview path.

## Operational Rules

- Do not log mnemonic, private keys, file keys, nonces, authentication tags, decrypted filenames with sensitive
  context, plaintext bytes or decrypted media paths.
- Do not add a server preview fallback for encrypted media.
- Do not write decrypted E2EE media to `Downloads`, `Pictures`, `DCIM` or other shared storage for preview.
- Do not bypass AES-GCM authentication failures to enable partial video playback.
- If an Android or Media3 API requires a persistent plaintext temp file for E2EE media, stop that implementation
  path and document the limitation before proceeding.
